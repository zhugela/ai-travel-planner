# Agent Harness 全景

> **什么是 harness**:包在模型外面的那一整套东西——让模型"能做事"的所有装置。
> 模型负责"想",harness 负责"想出来的东西能落地"。
>
> 本文回答三个问题:
> 1. 我的 harness 由哪些部件组成?
> 2. 每个部件管什么、坏了会怎样?
> 3. 换模型时,哪些要动、哪些不用动?
>
> 最后更新:2026-11-10

---

## 一、一句话结论

> **模型可以换,harness 不能塌。**
> 本项目从百炼切到 DeepSeek,业务代码几乎没改 —— 因为 harness 依赖的是抽象接口,不是具体厂商。

---

## 二、harness 的五个部件

```
                    ┌─────────────────┐
   用户输入  ───────▶│  ① 输入装配     │  提示词 + 历史 + 工具清单 + 能力说明
                    └────────┬────────┘
                             ▼
                    ┌─────────────────┐
                    │  ② 模型调用     │  ChatModel 抽象(可替换)
                    └────────┬────────┘
                             ▼
                    ┌─────────────────┐
                    │  ③ 行动执行     │  工具调用 + 权限 + 结果回填
                    └────────┬────────┘
                             ▼
                    ┌─────────────────┐
                    │  ④ 循环控制     │  状态机 + 步数上限 + 死循环检测
                    └────────┬────────┘
                             ▼
                    ┌─────────────────┐
                    │  ⑤ 输出协议     │  SSE 事件 + 结束信号 + 错误处理
                    └────────┬────────┘
                             ▼
                         用户看到
```

**任一环断了,整条链都跑不通。**

## 三、逐个部件

### ① 输入装配

| 项 | 本项目实现 | 坏了会怎样 |
|---|---|---|
| 系统提示词 | `YuTravelAgent.systemPrompt` | 规则冲突 → 答非所问 |
| 对话历史 | `BaseAgent.messageList` | **记录不全 → 重复调用 20 次** |
| 工具清单 | `AgentController.availableLocalTools()` | 给了不可用工具 → 反复撞墙 |
| 能力边界说明 | `buildCapabilityNote()` | 模型不知道缺什么 → 瞎试 |

**核心原则**:模型没有记忆。**它看到什么,取决于你给它什么。**

**本项目的坑**:
- 存历史时丢了 `toolCalls` 字段 → 模型看不到自己下过指令
- 工具结果没回填 → 模型不知道执行结果
- 没配好的工具照样给 → 模型反复试探

→ 详见 [AGENT_DESIGN.md](../guides/AGENT_DESIGN.md) 坑 1、2

---

### ② 模型调用

| 项 | 本项目实现 |
|---|---|
| 抽象接口 | Spring AI `ChatModel` |
| 当前实现 | DeepSeek(OpenAI 兼容协议) |
| 备选 | DashScope qwen / Ollama 本地 |

**设计要点**:所有业务代码依赖 `ChatModel` 接口,不依赖具体厂商。

**换模型时要改的**:
```yaml
spring.ai.model.chat: openai      # 选哪个实现
spring.ai.openai.base-url: ...    # 指向哪个服务
spring.ai.openai.chat.options.model: deepseek-chat
```

**换模型时不用改的**:
- Agent 四层继承
- 工具定义
- Prompt 模板
- RAG 检索
- SSE 输出

**验证过的事实**:百炼欠费当天,切换 DeepSeek 后项目照常运行,业务代码零改动。

---

### ③ 行动执行

| 项 | 本项目实现 | 坏了会怎样 |
|---|---|---|
| 工具注册 | 反射遍历 `@Tool` 注解 | 漏注册 → 模型没有该能力 |
| 权限/门控 | `health()` + `availableLocalTools()` | 给不可用工具 → 撞墙 |
| 参数校验 | `@ToolParam` + 工具内校验 | 非法输入 → 异常 |
| 结果回填 | `ToolResponseMessage` | **不回填 → 模型看不到结果** |

**核心原则**:模型说"我要调 X",harness 要负责**执行 + 把结果告诉它**。

**本项目的坑**:
- `act()` 只把结果拼进返回字符串,没写回历史 → 模型"失忆"
- `TerminateTool` 没注册 → 模型没有"结束"这个动作

→ 详见 [AGENT_DESIGN.md](../guides/AGENT_DESIGN.md) 坑 2、3

**安全边界**:
- `TerminalTool` 白名单
- `FileOperationTool` 路径校验(**当前缺失,已知短板**)

---

### ④ 循环控制

| 项 | 本项目实现 | 默认值 |
|---|---|---|
| 状态机 | `AgentState` (IDLE/RUNNING/FINISHED/ERROR) | — |
| 步数上限 | `BaseAgent.maxSteps` | 10(Agent 为 20) |
| 死循环检测 | `LoopGuard` | 同工具 3 次 / 无进展 5 次 |
| 超时 | `SseEmitter(300_000L)` | 5 分钟 |
| 状态生命周期 | `StateContext` (AutoCloseable) | try-with-resources |

**核心原则**:模型不知道什么时候该停,**停止条件必须由 harness 定义**。

**本项目的坑**:
- 无工具调用时没置 FINISHED → 空转到 maxSteps
- 只靠 maxSteps 兜底 → 能停,但停了 20 步全是浪费

→ 详见 [AGENT_DESIGN.md](../guides/AGENT_DESIGN.md) 坑 4

---

### ⑤ 输出协议

| 项 | 本项目实现 | 坏了会怎样 |
|---|---|---|
| 传输方式 | SSE (`text/event-stream`) | — |
| 事件类型 | `step` / `loop` / `error` / **`done`** | **缺 done → 浏览器重连重复执行** |
| 连接释放 | `onTimeout` / `onCompletion` / `onError` | 客户端断开 → 句柄泄漏 |
| 前端解析 | 按 `Step N:` 分块聚合 | 逐条处理 → 内容被拆碎 |

**核心原则**:服务端"结束"和客户端"理解结束"是两件事,**必须显式对齐**。

**本项目的坑**:
- 只 `complete()` 不推 `done` → EventSource 按规范自动重连 → 重复执行
- 多行 `data:` 被拆成多次回调 → 前端逐条处理导致内容丢失

→ 详见 [API_CONTRACT.md](./API_CONTRACT.md) 第四节

## 四、部件与坑的对应关系

| 坑 | 所属部件 | 性质 |
|---|---|---|
| 1 历史丢 toolCalls | ① 输入装配 | 信息不完整 |
| 2 结果未回填 | ③ 行动执行 | 信息不完整 |
| 3 未注册 TerminateTool | ③ 行动执行 | 信息不完整 |
| 4 无工具调用未结束 | ④ 循环控制 | 语义没对齐 |
| 5 未推 done | ⑤ 输出协议 | 语义没对齐 |

> **3 个"信息不完整" + 2 个"语义没对齐" = 全在模型外面,模型本身没问题。**

## 五、换模型时的检查清单

| 部件 | 换模型是否受影响 |
|---|---|
| ① 输入装配 | ⚠️ 提示词可能要调整(不同模型对指令的敏感度不同) |
| ② 模型调用 | ✅ **只改配置** |
| ③ 行动执行 | ⚠️ 工具调用格式可能有差异(函数名/参数 schema) |
| ④ 循环控制 | ✅ 不受影响 |
| ⑤ 输出协议 | ✅ 不受影响 |

**结论**:换模型真正要盯的是 ① 和 ③,其余两类只改配置。

**本项目的实际经历**:百炼 → DeepSeek 只改了 `application.yml`,① 的提示词后来发现要重写(报告场景),③ 的工具调用是 OpenAI 兼容格式,无改动。

## 六、harness 的调试方法

**现象 → 看哪个部件**

| 现象 | 先查部件 | 具体看什么 |
|---|---|---|
| 反复调同一工具 | ① 输入装配 | 历史里有没有 toolCalls |
| 模型说"没拿到数据" | ③ 行动执行 | 结果有没有回填 |
| 停不下来 | ④ 循环控制 | 有没有结束条件 |
| 重复执行整个任务 | ⑤ 输出协议 | 有没有推 done |
| 答非所问 | ① 输入装配 | prompt 有没有冲突 |
| 说"我做不到" | ① 输入装配 | 能力说明有没有给对 |

**排查顺序**:先看 ⑤(最容易查)→ ④ → ③ → ①(最难,涉及 prompt 设计)。

## 七、已知短板

| 短板 | 影响 | 状态 |
|---|---|---|
| 文件路径无校验 | 模型可写任意路径 | 未修 |
| 会话记忆存本地文件 | 多实例部署会串数据 | 未解 |
| 真实部署未验证 | 并发、隔离、限流都没测过 | 跳过 |
| 工具超时控制粗糙 | 单个工具卡住会拖垮整轮 | 未优化 |

## 八、一句话记住

> **模型的聪明程度由厂商决定,能干多少活由 harness 决定。**
> 追模型追不完,把 harness 做扎实,换谁都一样。
