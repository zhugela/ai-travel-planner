# Prompt 编写规范与冲突检测清单

> **为什么需要这份文档**
> 本项目出现过 3 次"模型输出跟输入没关系"的事故,根因都不是知识库不足,
> 而是 prompt 之间互相冲突、或数据结构装不下要求的输出。
> 每次新增/修改 prompt 前,先过一遍本文的自检表。
>
> 最后更新:2026-11-10

---

## 一、三次事故复盘

| # | 现象 | 真实根因 | 当时误判 |
|---|---|---|---|
| 1 | 智能行程页输入「成都 5 天带爸妈」,输出 5 条追问而非行程 | `travel-system.st` 规定"信息不全禁止输出行程,仅允许追问",而报告页复用了这份 prompt | "RAG 知识库不完整" |
| 2 | 追问被塞进 `suggestions[]` 当"建议展示" | `TravelReport(title, List<String>)` 只有字符串列表,装不下分天行程,模型只能硬塞 | "模型不会规划" |
| 3 | 旅行工具页问"机票均价",模型去抓维基百科写文件 | `YuTravelAgent` prompt 无"工具做不到时怎么办"的兜底约束 | "工具不够多" |

**共同点**:三次都不是数据问题,是**约束缺失**。

## 二、写 Prompt 前必答的 6 个问题

### Q1: 这份 prompt 是给哪个场景的?
对话 / 结构化报告 / 工具型 Agent,三者的输出契约完全不同:

| 场景 | 输出形态 | 缺信息时 |
|---|---|---|
| 对话 | 自然语言 | **可以追问**(这是对话的价值) |
| 结构化报告 | 固定 JSON 结构 | **必须用默认值补齐**,不能追问 |
| 工具型 Agent | 工具调用 + 最终答复 | **说明缺什么能力**,不能用无关工具凑 |

**规则:不同场景禁止复用同一份 system prompt。** 报告页必须用独立 prompt。

### Q2: 输出的数据结构装得下 prompt 里要求的内容吗?
要求"每天包含交通/景点/餐饮/住宿/花费",对应的 record/class 就必须有这些字段。

```java
// ❌ 装不下 —— prompt 要求分天行程,结构只有字符串列表
record TravelReport(String title, List<String> suggestions) {}

// ✅ 装得下
record TravelReport(
    String title, String summary,
    List<DayPlan> days, Budget budget,
    List<String> assumptions, List<String> tips) {}
```

**检查方法**:prompt 里每提到一个输出要素,去数据结构里找对应字段。找不到就是 bug。

### Q3: 缺信息时的策略写清了吗?
必须显式二选一,**不允许含糊**:

- 「信息不足时追问用户」→ 用于对话场景
- 「信息不足时采用默认值,并写入 assumptions 字段」→ 用于报告场景

本项目事故 #1 就是这句话没在报告 prompt 里重写,继承了对话版的"追问"。

### Q4: 有没有和别的 prompt 冲突?
本项目实际冲突示例:

| 来源 | 规则 | 冲突点 |
|---|---|---|
| `travel-system.st` | 信息不全禁止出完整行程,仅追问 | 报告要一次出完整行程 |
| 报告附加指令 | 每次都要生成旅行规划结果 | 与上面直接矛盾 |

模型在两个矛盾指令间会随机选一个,表现就是"时好时坏"。

**检查方法**:grep 所有 `.st` 文件里的"禁止""必须""不要",逐条比对当前 prompt。

### Q5: 做不到的时候怎么办?
工具型 Agent 必答。本项目事故 #3:

```
# ❌ 原 prompt —— 没说工具不够时怎么办
1. 景点、天气仅允许调用工具获取,禁止编造;
2. 数据齐全后调用 TerminateTool 输出完整行程;
```

模型遇到"机票均价"(没有机票 API)时,为了满足"输出完整行程"而抓网页凑步骤。

```
# ✅ 补上兜底
3. 若现有工具无法完成任务(如查机票、订酒店),直接说明缺哪项能力并建议用户手动查询,
   禁止用无关工具凑步骤;
```

### Q6: 结构化输出能不能被解析?
用 `chatClient...entity(Xxx.class)` 时:
- 字段必须有明确类型(不要 `Object`)
- 数值字段标明单位(元/人/天)
- 数组字段允许为空,但要能在 prompt 里说明"没有就给空数组"

### Q7: 工具在运行时真的可用吗?
**能力门控是架构问题,不是 prompt 问题。** 靠 prompt 让模型"别调用不可用工具"是治标。

正确做法是**不把不可用的工具注册给模型**:

```java
// ❌ 全部无条件注册 —— 模型只能撞墙才知道哪个不可用
Object[] tools = { fileTool, webSearchTool, pdfTool, ... };

// ✅ 先探测,不可用的不注册
public record Health(boolean available, String reason) {}
WebSearchTool.Health h = webSearchTool.health();
if (h.available()) tools.add(webSearchTool);
else log.warn("跳过联网搜索: {}", h.reason());
```

同时把边界写进 system prompt,让模型不用试探:

```
【当前不可用的能力】
联网搜索(未配置 SEARCH_API_KEY)
以上能力未启用,用户要求这类任务时直接说明无法完成,禁止用其他工具拼凑步骤来假装完成。
```

**效果对比(本项目实测)**:

| | 问「机票均价」的结果 |
|---|---|
| 门控前 | 4 轮:调天气 → 搜索失败 → 查状态 → 中英混杂道歉 |
| 门控后 | 1 轮:直接说明缺少机票查询能力 + 建议用户去携程查 |

每个有外部依赖的工具都应实现 `health()`:
- 依赖密钥的 → 检查密钥是否为空
- 依赖外部服务的 → 启动时 ping 一次
- 纯本地工具 → 恒返回 available,不需要实现

## 三、自检清单(复制到 PR 描述里勾)

```
[ ] 1. 场景判定:对话 / 报告 / Agent,未复用其他场景 prompt
[ ] 2. 结构对齐:prompt 要求的每个输出要素,数据结构都有对应字段
[ ] 3. 缺失策略:明确写了"追问"还是"用默认值 + assumptions",没有含糊
[ ] 4. 冲突检查:grep 过所有 .st 文件,无相反指令
[ ] 5. 兜底规则:Agent 类 prompt 写了"工具做不到怎么办"
[ ] 6. 输出可解析:entity() 的字段类型明确、单位标明、空数组可接受
[ ] 7. 能力门控:有外部依赖的工具实现了 health(),不可用的不注册给模型
```

## 四、本项目 Prompt 资产清单

| 文件 | 场景 | 关键约束 |
|---|---|---|
| `prompts/travel-system.st` | 对话 | 信息不足时追问 1-2 个问题 |
| `prompts/travel-rag-system.st` | RAG 问答 | 只基于上下文,无命中直接说"暂无相关旅游攻略信息" |
| `prompts/destination-recommend-system.st` | 目的地推荐 | 列表格式输出 |
| `TravelApp.REPORT_SYSTEM_PROMPT` | 结构化报告 | 禁止追问、必须补齐天数、每日三段具体安排、预算贴近用户给定值 |
| `YuTravelAgent.systemPrompt` | 工具型 Agent | 工具优先、禁重复调用、能力不足要直说 |

**注意**:`travel-system.st` 已含"信息不全禁止输出行程"规则。
**任何需要"一次给完整方案"的新场景,都不能复用它**,必须写独立 prompt。

## 五、验证方法

改完 prompt 别只看一次输出,跑这 3 类用例:

| 用例类型 | 示例 | 期望 |
|---|---|---|
| 信息完整 | 「成都 5 天,2 人,预算 5000,带爸妈」 | 直接出完整方案 |
| 信息残缺 | 「成都 5 天」 | 报告场景:用默认值补齐 + assumptions 标注 |
| 超出能力 | 「对比北京西安机票均价」 | Agent 场景:直说没有机票查询能力 |

**判定标准**:输出形态要跟场景契约一致,不是"看起来像那么回事"。
