# 知识沉淀工作流

> 状态:已采用
> 目标:让“解决一次问题”自然变成“以后少踩一次坑”
> 最后验证:2026-11-10

## 最小习惯

每次完成任务前花 10 分钟回答四个问题:

1. 这次真正的根因是什么?
2. 哪条规则能防止它在别的项目重演?
3. 如何用一个测试或检查清单证明规则生效?
4. 这是普通知识卡片,还是需要长期解释取舍的 ADR?

如果四个问题答不出来,先不要写长文;在任务里留一条待验证结论即可。

## 六步流程

### 1. 捕获

在问题刚解决时记录现象、根因、证据和验证方式。不要依赖几天后的记忆。

### 2. 去项目化

把“某个类第几行报错”提升为可迁移规则,但保留项目文件作为证据。规范与当前实现必须分开写。

### 3. 分类

本知识库只保留五类:
- `security`:安全边界与风险响应。
- `rag`:知识检索、向量化和质量评测。
- `agent`:状态机、工具与流式生命周期。
- `engineering`:测试、交付和协作流程。
- `templates`:可以直接复制的模板。

找不到分类时,先放最接近的一类,不要为一篇文档新建顶层目录。

### 4. 去重与链接

- 一个页面只讲一个核心实体或问题。
- 新结论优先更新已有页面,不要创建“最终版2”。
- 页面至少链接一个相关规范、ADR 或模板。

### 5. 标状态

每页写清 `提议 / 部分采用 / 已采用`。代码还没改时只能写“提议”,不能让文档制造虚假的完成感。

### 6. 验证与登记

- 检查索引能找到新页面,链接和项目证据存在。
- 更新 `docs/knowledge/log.md`。
- 重要技术取舍新增或更新 ADR。
- 代码变更同步更新需求、任务、测试和接口契约。

## 什么写在哪里

| 内容 | 位置 |
|---|---|
| 当前项目怎么调用某接口 | `docs/guides/` |
| 换项目仍适用的规则 | `docs/knowledge/` |
| 为什么选 DeepSeek/本地 Embedding | `docs/adr/` |
| 当前需求、任务、测试状态 | `docs/project/` |
| 课程原始笔记 | `docs/notes/` |
| 运行时供 RAG 检索的业务资料 | `src/main/resources/document/` |

## 每周轻量整理

- 合并重复页面,修复失效链接。
- 将已经落地并验证的页面从“提议”改为“已采用”。
- 将过期方案标记“已废弃”,保留替代链接。
- 从本周问题中只选 1~3 条高复用结论,避免知识库变成日志堆。

## 质量检查

- [ ] 标题能说清问题,不是“杂记”“总结2”。
- [ ] 事实、建议和待办已分开。
- [ ] 有根因或决策背景,不是只贴代码。
- [ ] 有可执行规则和验收方法。
- [ ] 有适用边界和项目证据。
- [ ] 有相关链接,索引和 log 已更新。
