# 密钥生命周期与泄露响应

> 状态:部分采用
> 来源:项目安全审查
> 最后验证:2026-11-10

## 问题

API Key 一旦进入源码、测试文件、配置默认值、日志或 Git 历史,删除当前文件中的值并不等于风险消失。真正目标是让密钥可轮换、可撤销、最小权限且不被持久化。

## 可复用规则

1. 代码仓库只保存变量名,不保存可工作的默认密钥。
2. 生产配置缺少必需密钥时应启动失败,不要静默降级到内置值。
3. 开发、测试、生产使用不同密钥和权限,测试优先使用 Mock。
4. 日志不打印请求头、完整配置、Prompt 中的凭证或第三方原始错误体。
5. 怀疑泄露时先撤销/轮换,再清理代码和历史;顺序不能反。
6. 给密钥设置调用额度、来源限制、告警和定期轮换日期。

推荐配置形态:

```yaml
provider:
  api-key: ${PROVIDER_API_KEY}
```

不推荐:

```yaml
provider:
  api-key: ${PROVIDER_API_KEY:一个可工作的默认值}
```

## 泄露响应清单

- [ ] 立即在服务商控制台撤销旧密钥并创建新密钥。
- [ ] 检查调用账单、来源 IP、异常时间段和权限范围。
- [ ] 搜索源码、测试、文档、日志、构建产物和环境快照。
- [ ] 删除硬编码和非空默认值,改为环境变量或密钥管理服务。
- [ ] 如密钥进入 Git 历史,评估清理历史;即使清理也必须先轮换。
- [ ] 增加提交前密钥扫描和 CI 扫描。
- [ ] 记录泄露原因、影响范围和防复发措施,不要记录密钥本身。

## 验收方法

正向:
- 配置正确的环境变量后,应用能启动并完成一次受控调用。

反向:
- 清空环境变量后,生产配置启动失败并给出“缺少配置”,日志不出现密钥内容。

仓库扫描:
- 搜索常见密钥前缀、`api-key:` 非空值和测试类中的字符串常量。
- 检查 `git diff --cached` 与 Git 历史,不能只查工作区。
