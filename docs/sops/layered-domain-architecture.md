# SOP：分层领域架构搭建

## 适用场景

- 新功能涉及多个包或多个外部依赖。
- Controller、Service、Agent、Tool 的职责开始混在一起。
- 同一段逻辑在不同入口重复。

## 步骤

### 1. 写出用户行为

用一句话写清入口和结果：

```text
用户通过 <入口> 提交 <输入>，系统应返回/流式输出 <结果>，
失败时用户看到 <状态>。
```

不要从类名开始设计。

### 2. 划分领域

对每个领域回答：

- 谁拥有状态？
- 谁发出外部请求？
- 谁负责校验权限和参数？
- 失败由谁转换为用户可见错误？

本项目参考划分：

| 领域 | 拥有数据/状态 | 外部依赖 |
|---|---|---|
| Chat | 会话消息 | ChatModel、文件记忆 |
| Report | 报告输出契约 | ChatModel 结构化输出 |
| RAG | 文档、向量、检索参数 | 本地 Embedding、DeepSeek |
| Agent | 运行状态、步骤、循环检测 | ChatModel、Tools |
| Tools | 单次操作结果 | 文件、网络、PDF、终端 |

### 3. 定义依赖方向

```text
Controller -> Application -> Domain/Agent -> Ports/Adapters
```

硬规则：

- Controller 不直接操作文件、数据库或厂商 SDK。
- Tool 不决定 Agent 何时停止。
- Prompt 不承担参数校验。
- 领域对象不依赖 Web 响应结构。

### 4. 先定义契约

每个跨层调用先写：

- 输入类型和允许范围。
- 输出类型。
- 超时、错误和取消。
- 是否需要用户身份或授权。

HTTP/SSE 契约同步到 `docs/guides/API_CONTRACT.md`。

### 5. 设计测试边界

至少写三类测试：

1. 领域主路径。
2. 外部依赖失败。
3. 权限/输入边界。

外部模型和网络优先 mock；真实端到端验证单独记录。

### 6. 小步迁移

- 先新增边界，不立即删除旧路径。
- 用测试证明新旧行为一致。
- 一次只迁移一个入口。
- 删除旧路径后再更新架构文档。

### 7. 完成检查

- [ ] 分层职责与 `ARCHITECTURE.md` 一致。
- [ ] 依赖方向没有反向穿透。
- [ ] 接口契约已同步。
- [ ] 外部失败有测试。
- [ ] 没有新增隐藏权限边界。
