# SOP：本地可观测性与反馈回路

## 目标

让问题在本地可复现、可定位、可验证修复，不依赖猜测。

## 1. 先定义要回答的问题

示例：

- 一次 RAG 请求慢在检索还是生成？
- Agent 为什么调用同一工具？
- SSE 是正常结束、断开还是重复重连？
- 文件工具是否拒绝了越界路径？

没有问题就不先堆监控。

## 2. 最小日志基线

每个关键请求至少有：

- `requestId` / `traceId`。
- 入口和耗时。
- 模型/检索/工具阶段。
- 成功、失败、超时、取消。
- 关键数量：检索命中数、工具调用次数、流式帧数。

禁止记录：

- API Key。
- 完整 Prompt、完整回答和完整聊天历史。
- 未经脱敏的本机绝对路径。

## 3. 本地反馈环

```text
复现命令
  -> 结构化日志
  -> 针对性测试
  -> 最小修复
  -> 同一命令重跑
  -> 记录前后差异
```

本项目起步命令：

```powershell
.\mvnw.cmd test -Dtest=RagRetrieverEnhancerTest
Get-Content .\tmp\run.log -Tail 100
```

## 4. 指标建议

| 领域 | 指标 |
|---|---|
| HTTP/SSE | 请求数、状态码、持续时间、活动连接数 |
| Chat | 首 token 延迟、总耗时、失败率 |
| RAG | 检索耗时、topK、命中数、相似度、兜底率 |
| Agent | 步数、工具次数、循环终止、done/error 比例 |
| Tools | 工具名、耗时、成功/拒绝/失败、输出大小 |

先做本地日志和测试断点，再考虑 Prometheus/Grafana 等栈。

## 5. 反馈闭环

每次修复后：

1. 用同一复现步骤重跑。
2. 对比修改前后日志或指标。
3. 保存关键证据路径。
4. 更新 `feature_list.json` 或技术债。
5. 若规则可机械化，补测试而不是只写文档。

## 6. 清理

- 删除一次性 debug 日志。
- 生产默认不使用 DEBUG。
- 不保留无指标的 Dashboard。
- Harness 组件若不能改善定位速度，做 A/B 对比后移除。
